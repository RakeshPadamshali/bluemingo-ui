## 0. Organisation

### 0.1 Ownership and landing
Operations is a **platform** module: every table lives in the production-confirmation application (`mes_*`, MES PC Flyway) and is raised as change requests **OPS-R-01 … OPS-R-14** in `Requests-OPS.md`. Four touchpoints are Quality-owned and land as QA Data-Model **§30** (hot-out re-roll decision, bar segregation entry, auto-clearance on ERP confirmation feedback, GMM hardness and downstream sampling) — they read and write the platform tables designed here the way the sample hand-off already does. The Allocation application receives no new item (ALC-R-05 … 08 of the PPC pass cover swap effects and the feed). Nothing inside either application is coded from here.

### 0.2 Conventions
As the QA Data-Model §2, the MDM design §0.2 and the PPC design §0.2: PK `<entity>_id bigint`; **`+ audit tail`**; `(Y)` nullable; scope key set S and resolution rule **R-S**; `effective_from/to` informational until P3. Product-agnostic per D0: units, pulpits, furnaces, bases, hooks, boxes, bunkers and machines are `mes_operations` / `mes_equipments` rows (types are data), never columns. Additional vocabulary of this design: **pulpit** = a control station = a `pulpit_code` shared by the operations its screen hosts; **stage event** = a timestamped fact about a material at a station; **device** = a registered scanner / scale / printer / sensor; **message** = a staging row for the Level-1/2 or ERP exchange with a status. Flags: `[P4]` the device foundation is deferred — the records and the manual fallback are designed, the transport is not; `[D-08]` Level-1/2 exchange designed as messages under the assumption that it is in scope; `[D-01]` ERP posting designed MES-side only; `[D-05]` ABGM in scope.

### 0.3 Live facts that shaped the design (verified 2026-09-15)
- **Confirmation card:** `mes_production_confirmation` (27 rows — 15 manual, 10 `is_auto`, 2 dummy size-setting; statuses CONFIRMED / REVERSED) carries `delay_reason`, `hold_reason`, `is_rework`, `original_confirmation_id`, `charge_id`; `mes_pc_screen_config` resolves ~35 behaviour flags per (factory, operation) — `confirmation_basis` (MATERIAL / CHARGE), `qty_capture_mode` (WEIGHT / BOTH), `require_material_charging`, `require_sequencing_before_charge`, `enforce_inward_release`, `block_charge_on_failed_chemistry`, `piece_weight_tolerance_pct`, `allow_next_operation_select`, `require_next_operation`, `allow_sample_generation`. The pipeline PC1–PC17 (eligibility, material-number cascade, consumption, batch granularity, mass balance, loss / yield engine, next-operation promotion) runs for every operation.
- **Charging:** `mes_charges` (charge_no, operation, equipment, status OPEN / RELEASED, totals) and `mes_inventory_charges` (inventory × charge, charged qty / pieces) — no scan, no weight, no timestamps, no sequence position on the line; target-piece charging (ChargeMath), release and reconciliation exist.
- **Losses:** `mes_operation_loss_config` per operation (BL Burning Loss PERCENT, EC End Cut VALUE, MR Mis-Roll, REJECT; basis CHARGE; `captures_pcs`, `deduct`, `scrap_sku_code`, `seq`) → `mes_production_loss` per confirmation (`capture_mode`, `loss_pct`, `loss_qty`, `loss_pcs`); `validate_loss_formula` is the yield check.
- **Process parameters:** `mes_process_attributes` (6 rows: target / lower / upper / `default_captured_from`) → `mes_process_parameters_captured` (attribute, value, `captured_from`; no rows yet) — the MDM design already scopes the master by equipment, PSN, grade family, size family and adds `validation_mode`.
- **Identity:** `mes_batches` (batch_number, confirmation, generated-at operation, quantity, pieces, length_min / length_max, remarks); `mes_batch_relations` MERGE 8 / SPLIT 1 / TRANSFORM 7; `mes_batch_number_generation_config` per operation with `config_json` grouping = Bundle (Cooling Bed Report, RCS Bundling Report; `capture_length`, `short_length_attribute`, `cut_multiplier_attribute`, `child_format`); planned → actual rename cascade at heat generation (`mes_heat_generation.planned_material_number`, propagated across schedule materials, children and allocations).
- **Inventory:** `mes_inventory` (RM / IM / DUMMY; AVAILABLE / PRODUCED / SCRAPPED; `ud_status`, `prev_operation` / `next_operation`, `routing_complete`, `salvage_id`, `stage_item_code`, `operation_assigned_by`); holds `mes_inventory_holds` with `mes_hold_reasons` (Quality Investigation, Contamination Suspected, Planner Hold); the PPC pass adds `current_equipment_id`, `location_code`, `scan_status`, `planned_material_number`.
- **Routing:** `mes_process_routings` + `mes_operation_routings` (131) with attribute-scoped routings (`mes_routing_attr_value`: Shape, Execution, Grade group, HTC Code, HT Condition, Customer FG Size, Customer Length); equipment routing `mes_operation_equipment_routing` + `mes_oer_rule` (input → output attribute rules) + `mes_equipment_linkage` (previous → next equipment); `mes_operations.allow_manual_sequencing` / `sequence_by_equipment` are set on the rolling operation only.
- **Secondary equipment:** `mes_secondary_equipments` (ROLL, BLADE … with `life_limit`) → `mes_secondary_equipment_instance` (`life_limit_consumed`) → usage per confirmation. `mes_equipment_speed` (850 rows) is the rate source; `mes_billet_master` (57 rows, grade series × size → `wt_per_meter`) is the theoretical-weight source; `mes_shape_weight_master` (13) the shape factor.
- **Sampling and reversal:** `mes_production_sample` (sample ref, batch, heat, `draw_position`, weights, status, issued / received, `qc_sample_id`, `sampling_rule_id`, `storage_location`) + `mes_production_sample_test`; `mes_production_reversal` (PC / HEAT_GENERATION). Dispatch: `mes_uid_dispatch`, `mes_dispatch_challan` (+ line).
- **Delay reasons:** `mes_delay_reasons` (Mechanical Breakdown, Electrical Breakdown, Waiting for Raw Material, Utility Shortage; category unused) — MDM §5.6 adds class, hierarchy, scope and the maintenance plan.
- **Absent everywhere (223 tables, both code bases):** barcode / scan columns, weighing, labels, Level-1/2 messages, ERP outbound, downtime events, hot-out, shift log, annealing jobs, packs / bags, GMM objects, virtual identities, cut plans.

## 1. Cross-cutting decisions for Operations

| # | Decision | Rationale |
|---|---|---|
| **M-OPS-01** | **One confirmation engine, many pulpits.** Every station — furnace, roughing, finishing, gas cutting, cooling bed, the downstream lines — runs the built confirmation pipeline under a per-operation screen configuration; a pulpit is a group of operations sharing a `pulpit_code`; three pulpit modes (full card, acknowledge-only, single-action HMI). No second execution engine. | BRD 9.1 additional point 1, PLT-001…003, CHG-001; row 2 review note ("configuration on the existing screen"). |
| **M-OPS-02** | **Stage events are the tracking substrate.** Arrive, charge, discharge, start, complete, acknowledge, declare, hot-out, cobble, divert are rows of `mes_stage_event` written by the screens, the scans, the Level-2 messages and the engine — the one source for pulpit hand-over, dwell times, downtime linkage, Level-2 timestamps, the shift log and the reports. | PLT-002, 9.15.1 (PDO timestamps per stage), DWN-003. |
| **M-OPS-03** | **Identity capture is a record, not a device** `[P4]`. Scans, weighings and label prints are rows (`mes_scan_event`, `mes_weighing_event`, `mes_label_print`) referencing a `mes_device` row, each with a manual fallback and a validation trail; the device transport is the deferred device foundation. | CHG-001…008, BND-001, F8.1-14, F9.5-01, GMM-002; scope decision 2026-09-12. |
| **M-OPS-04** | **Virtual identity reuses the planned-number cascade.** A virtual id is a placeholder inventory row whose number is the heat's planned number (or a VID series when no heat is known); the built planned → actual rename on arrival closes the loop; ERP messages for it are held until reconciliation. | VID-001…006, 9.6 additional point; row 7 finding ("the planned-number cascade is the reusable core"). |
| **M-OPS-05** | **ERP posting is a queue with a bypass switch, MES side only** `[D-01]`. Every ERP-relevant event writes `mes_erp_outbound`; the send is manual multi-select at the mills or automatic per unit; bypass is a privileged switch with background synchronisation and an ordering rule (input weight before output). | SAP-001…006, 9.15.1 (manual batch-report trigger), ANL-004/009/011, DSP-001. |
| **M-OPS-06** | **Level-1/2 exchange is a message ledger** `[D-08]`. PDI / PDO, charge and discharge feedback, run / stop, parameter sets and actuals, cycle download and SCADA status are `mes_l2_message` rows with status, latency, duplicate and acknowledgement flags; the HMI / historian is a message source, not a second interface. | RHF-004, MO-006, PLT-004, IBA-003, 9.15.1, F8.1-13, F9.1-05, F9.2-03. |
| **M-OPS-07** | **Losses, declarations and yields are configuration.** Loss classes (scale, end cut, cobble, mis-roll, sample, hot-out, shear, invisible, segregation) are rows of the built loss configuration; the product declaration (prime / hot-out / indirect hot-out / cobble / TMT / scrap) is a vocabulary on the confirmation; yields are views over confirmations, losses and the yield master. | MO-005…007, HO-003…005, BLM-005, ANL-004, GMM-007…011, F8.1-12, F8.2-17. |
| **M-OPS-08** | **Downstream units get objects only where the built card has none:** annealing / pickling jobs (base, hook, furnace, cycle), packs and bags, GMM bar outputs and bunkers, code-conversion events. Grinding, peeling, reeling, centreless grinding, MPI and cutting are the built card on routing operations. | Rows 12 … 12.5 verdicts ("generic execution exists"). |
| **M-OPS-09** | **Masters come from the Master Data design** (downtime reasons and maintenance plan, form conversion, batch derivation, section limits, process parameters, annealing load rules, HT cycles, yield, length, end discard, dimensional tolerance), **schedules from the PPC design** (rolling schedule and blocks, ABGM and downstream schedules, GMM lots, NCO declaration, swap engine), **clearances, sampling, defects, stickers and CAPA from the Quality module**. No Operations copy. | One book of record. |

## 2. Pulpit execution model — stations, stage events, pulpit notes *(rows 2, 16; PLT-001…003, IBA-002, SEQ-009, CHG-05, 9.1 additional point 1)* — PLATFORM

The five mill pulpits (Furnace, Roughing, Finishing, Gas Cutting, Cooling Bed) and every downstream station are the built operations with a station grouping and a screen mode. Acknowledging a stage at one pulpit is what activates the entry at the next — the built next-operation promotion already does the activation; the acknowledgement is the missing lightweight input.

- `mes_operations` gains **`pulpit_code varchar(30)`** (Y — the control station whose screen hosts the operation: FURNACE / ROUGHING / FINISHING / GAS_CUTTING / COOLING_BED / TPL / BAF / CRHF / GRINDER / PACKING … data; several operations share one pulpit) · `pulpit_sequence int` (Y — order of the pulpits along the line).
- `mes_pc_screen_config` gains **`pulpit_mode varchar(15)`** (FULL / ACKNOWLEDGE / HMI — FULL = the built confirmation card; ACKNOWLEDGE = select-and-acknowledge without re-entering batch data; HMI = single-action charging screen) · `show_sop_panel boolean` · `show_notes_panel boolean` · `show_declaration_panel boolean` · `show_downtime_panel boolean` · `dimension_check_mode varchar(10)` (NONE / WARN / BLOCK — finishing tolerance interlock) · `order_tolerance_mode varchar(10)` (NONE / WARN / NCO_PROMPT) · `require_scan_before_confirm boolean` · `charge_overrun_pieces int` (Y — the "order quantity + 1 billet" allowance at charging) · `mass_balance_tolerance_pct numeric(7,3)` (Y — bundle mix-up threshold) · `erp_trigger_mode varchar(10)` (AUTO / MANUAL — how confirmations reach the ERP queue) · `downtime_alert_minutes int` (Y — unplanned-downtime alert threshold) · `confirm_warning_text varchar(255)` (Y — one-way save warning before the final save) · `wallboard_enabled boolean` (unattended pulpit display of the queue and the notes).
- **`mes_stage_event`** — `stage_event_id` PK · `event_type varchar(20)` (ARRIVED / CHARGED / DISCHARGED / STARTED / COMPLETED / ACKNOWLEDGED / DECLARED / HOT_OUT / COBBLE / DIVERTED / HELD / RELEASED / SCANNED / WEIGHED / LABELLED / LOADED / UNLOADED — data) · `operation_id` FK `mes_operations` · `equipment_id` FK `mes_equipments` (Y) · `pulpit_code varchar(30)` (Y) · `inventory_id` FK `mes_inventory` (Y) · `batch_id` FK `mes_batches` (Y) · `schedule_material_child_id` FK `mes_schedule_material_childs` (Y) · `production_order_id` FK `mes_production_order` (Y) · `order_line_id` FK `mes_order_line_items` (Y) · `heat_number varchar(100)` (Y) · `event_at timestamptz` · `source varchar(10)` (MANUAL / SCAN / L1 / L2 / SCADA / SYSTEM) · `device_id` FK `mes_device` (Y) · `confirmation_id` FK `mes_production_confirmation` (Y — when the event is a confirmation) · `declaration varchar(20)` (Y — PRIME / HOT_OUT / INDIRECT_HOT_OUT / COBBLE / TMT / SCRAP — the product declaration at the rolling pulpit) · `next_operation_id` FK `mes_operations` (Y — the pulpit activated next) · `shift_id` FK `mes_shifts` (Y) · `user_id` FK `mes_user` (Y) · `remarks varchar(255)` (Y) · `payload_json jsonb` (Y) · **+ audit tail**.
- **`mes_pulpit_note`** — `note_id` PK · `note_type varchar(20)` (CAPA / INSTRUCTION / LAST_CAMPAIGN / DEVIATION / SOP_LINK / ALERT) · `pulpit_code varchar(30)` (Y) · S (`factory_id`, `operation_id`, `equipment_id`, `product_category_id`, `shape`, `size_min/max`, `grade`, `grade_series`, `customer_id`, `tdc_id`) · `title varchar(255)` · `body_text text` · `source_ref varchar(100)` (Y — the Quality NCR / CAPA id, the process-control deviation id or the campaign code) · `campaign_id` FK `mes_campaign` (Y) · `valid_from date` (Y) · `valid_to date` (Y) · `display_mode varchar(10)` (BANNER / PANEL / POPUP_ACK) · `ack_required boolean` · `priority int` · `effective_from/to` · **+ audit tail**.
- **`mes_pulpit_note_ack`** — `ack_id` PK · `note_id` FK `mes_pulpit_note` · `user_id` FK `mes_user` · `acknowledged_at timestamptz` · `batch_id` FK `mes_batches` (Y — the batch on screen when acknowledged) · **+ audit tail**.
- **R-OPS-01 — pulpit resolution (9.1 add. point 1, PLT-001):** a pulpit screen is the union of the queues of the operations carrying its `pulpit_code`; each operation keeps its own screen configuration (M-OPS-01); the wallboard mode shows the queue, the active notes and the running downtime timer without login.
- **R-OPS-02 — acknowledgement and hand-over (PLT-002/003):** in ACKNOWLEDGE mode the operator selects the entry and acknowledges; the system writes a COMPLETED stage event and an automatic confirmation carrying the incoming quantity (the built `is_auto` path), so losses, batch derivation and the next-operation promotion run unchanged and the entry appears at the next pulpit (the built PC step 9). FULL mode is the built card; HMI mode is the charging screen of §3. Worked example: billet B031140 acknowledged at ROUGHING 10:42 → auto-confirmation, COMPLETED event, entry CHARGED at FINISHING; Finishing declares PRIME 10:51 → the cooling-bed queue.
- **R-OPS-03 — notes on the pulpit (SEQ-009, CHG-04 "CAPA display", IBA-002):** notes resolve by R-S plus `pulpit_code` and the batch on screen; LAST_CAMPAIGN notes are generated from the deviations and corrections of the last three campaigns of the same PSN (process-control deviations and Quality CAPA, by `source_ref`); POPUP_ACK notes block the first confirmation of the shift until acknowledged.

## 3. Charging — scanner-driven *(row 5; CHG-001…010, CHG-04…08, BLM-001, SEQ-006…008, 9.4 additional point)* — PLATFORM

The built charging queue (charge, uncharge, target pieces, release, reconciliation, charge-basis confirmation) stays; what is added is the identification event, the validation trail, the sequence position, the weights and the timestamps on every charged line.

- **`mes_scan_event`** — `scan_event_id` PK · `scanned_code varchar(120)` · `scan_type varchar(15)` (BATCH / BUNDLE / COIL / SAMPLE / BAG / PACK / TAG) · `device_id` FK `mes_device` (Y) · `operation_id` FK `mes_operations` · `equipment_id` FK `mes_equipments` (Y) · `pulpit_code varchar(30)` (Y) · `scanned_at timestamptz` · `user_id` FK `mes_user` (Y) · `entry_mode varchar(10)` (SCAN / MANUAL / IMAGE — manual entry for missing or damaged stickers; image of the barcode or the paint-written id for verification) · `image_ref varchar(255)` (Y) · `resolved_inventory_id` FK `mes_inventory` (Y) · `resolved_batch_id` FK `mes_batches` (Y) · `result varchar(20)` (OK / NOT_FOUND / DUPLICATE / NOT_CLEARED / PSN_MISMATCH / OUT_OF_SEQUENCE / QTY_EXCEEDED / CODE_NOT_ALLOWED / SECTION_LIMIT / VIRTUAL_CREATED / OVERRIDDEN) · `validation_json jsonb` (Y — every check with its outcome) · `action_taken varchar(20)` (Y — CHARGED / REMOVED / SWAPPED / OVERRIDDEN / REJECTED / IDENTIFIED) · `override_action_code varchar(50)` (Y — the privileged action used) · `virtual_id` FK `mes_virtual_id` (Y) · `l2_message_id` FK `mes_l2_message` (Y — the PDI sent on this scan) · **+ audit tail**.
- `mes_inventory_charges` gains **`scan_event_id` FK `mes_scan_event` (Y)** · `charge_seq int` (Y — position in the charging order) · `planned_seq int` (Y — position in the released sequence) · `sequence_deviation boolean` · `deviation_action varchar(15)` (Y — REMOVE / SWAP / ACCEPT) · `psn_check varchar(10)` (Y — OK / MISMATCH / NA) · `production_order_id` FK `mes_production_order` (Y) · `theoretical_weight_kg numeric(12,3)` (Y) · `actual_weight_kg numeric(12,3)` (Y) · `weight_source varchar(12)` (Y — SCALE / THEORETICAL / ERP / MANUAL) · `charged_at timestamptz` (Y) · `discharged_at timestamptz` (Y) · `charge_ack_mode varchar(10)` (Y — OPERATOR / AUTO_L2) · `hot_out_id` FK `mes_hot_out_event` (Y) · `status varchar(15)` (CHARGED / DISCHARGED / HOT_OUT / REMOVED).
- `mes_charges` gains `production_order_id` FK `mes_production_order` (Y) · `block_id` FK `mes_rolling_schedule_block` (Y — the released block the charge serves) · `assigned_pieces int` (Y — the production-order quantity in pieces) · `overrun_allowance int` (Y — copied from the screen configuration at open).
- **R-OPS-04 — validation order at scan (CHG-003/004/006/009/010, BLM-001/002, CHG-06):** resolve the code to an inventory row (material number, batch number or Demand UID; the barcode carries only the id — every attribute is fetched); then, in order: exists (else NOT_FOUND → the virtual-id path of §5); cleared (the built inward release, usage decision and chemistry gates); code allowed at this step (form-conversion rules — CODE_NOT_ALLOWED with the forced-override prompt); section within the equipment limit for grinders; PSN of the batch equals the PSN pinned on the production order's line (PSN_MISMATCH refuses unless the privileged action CHARGE_PSN_OVERRIDE is used); duplicate — an active charge line in CHARGED or DISCHARGED for the same inventory refuses (a line in HOT_OUT does not: a returned billet is chargeable again); sequence — `charge_seq` versus `planned_seq` raises OUT_OF_SEQUENCE with the choices REMOVE, SWAP (the PPC swap engine, scenario BATCH_TO_BATCH — the sales-order swap usable by PPC and Operations) or ACCEPT (privileged); quantity — charged pieces of the production order ≤ `assigned_pieces + overrun_allowance` (the "order quantity + 1 billet" rule), else QTY_EXCEEDED; the next production order cannot start until the current one is complete unless the sequence was edited (PPC Manual Sequencing). Every outcome is a scan event with `validation_json`; nothing is added on the charging screen — additions and route or quantity changes happen in sequencing (SEQ-006), deletion is permitted.
- **R-OPS-05 — weights (9.4 additional point, CHG-003, SAP-006):** the actual weight comes from a weighing event when a scale is registered at the station (§10, `[P4]`), else the ERP-declared weight of the batch feed, else the theoretical weight = `wt_per_meter` (billet master) × length; `weight_source` records which; the input weight must be acknowledged by the ERP before the output confirmation is sent (§6 ordering rule).
- **R-OPS-06 — HMI screen and partial charging (CHG-001/002, CHG-04, SEQ-008):** the screen shows the released block in sequence with one action (charge) per scan; partial charging from several heats is the sequence order itself (a specified count from heat A, then B, then A again) — each charged line keeps its heat, so heat-wise counts and the return to a heat need no extra object; the sequence is transferred to the charging station by the Operations team (release of §4.6 of the PPC design).
- **R-OPS-07 — acknowledgement of charging (CHG-005):** where the furnace automation returns a charge feedback message (§11), `charge_ack_mode = AUTO_L2` and the CHARGED stage event is written by the message; otherwise the operator's charge action is the acknowledgement (BRM today — the open item OPEN-OPS-1 records the choice).

## 4. Reheating furnace *(row 6; RHF-001…005, HOT-001, F8.1-02, F8.2-04, F8.2-05)* — PLATFORM

RHF exposes two operations — charging (the §3 screen) and discharging / reheating confirmation — on the furnace pulpit; the standalone discharge screen may be folded into the rolling pulpit (RHF-005), which is a configuration choice, not a design branch.

- `mes_process_attributes` gains **`parameter_group varchar(30)`** (Y — ZONE_TEMPERATURE / HEATING / DESCALING / ROLLING / COOLING_BED / QUENCH / TEMPER — grouping on the SOP panel) · `zone_code varchar(20)` (Y — Z1 … Zn) · `l2_tag varchar(100)` (Y — the automation tag for the exchange; content only `[D-08]`) · `dwell_min_minutes int` (Y) · `dwell_max_minutes int` (Y — residence limits for furnace rows).
- **R-OPS-08 — SOP panel (RHF-001…003, IBA-001):** the furnace pulpit shows the parameter set resolved by R-S on (furnace equipment, PSN, grade family, size family) — zone set-points and heating parameters are master rows referenced by PSN, never stored on the PSN; several SOPs coexist as rows with different scope; actuals are captured on the confirmation (`mes_process_parameters_captured`, `captured_from` MANUAL or L2) and validated per `validation_mode` (MDM R-PP-02); PARAMETER_SET messages push the resolved set to the furnace automation where it exists (§11).
- **R-OPS-09 — dwell and discharge (F8.2-04, RHF-005):** dwell = `discharged_at − charged_at` on the charge line; the pulpit shows elapsed versus `dwell_min / dwell_max`; discharge writes the DISCHARGED stage event either from the discharge confirmation or from the rolling confirmation's `discharged_at` when the standalone screen is removed; HMD and pressure readings are L2 messages of type PARAMETER_ACTUAL (RHF-004).
- **R-OPS-10 — overstay (HOT-001):** a charged billet whose dwell exceeds `dwell_max_minutes` (or the post-descaling hold rule) gets a hot-out event of type OVERSTAY (§8) that needs the Quality decision before re-rolling.

## 5. Virtual ID and missing-batch handling *(row 7; VID-001…006, 9.6 additional point, 9.15.1 sensor swap)* — PLATFORM

- **`mes_virtual_id`** — `virtual_id` PK · `virtual_number varchar(60)` UQ · `reason varchar(25)` (ERP_DELAYED / HOT_CHARGE_GAP / MISSING_IN_HEAT / SENSOR_2M / OTHER) · `operation_id` FK `mes_operations` · `equipment_id` FK `mes_equipments` (Y) · `heat_number varchar(100)` (Y) · `planned_material_number varchar(60)` (Y — the planned number of the heat sequence the gap points at) · `expected_batch_number varchar(60)` (Y) · `grade varchar(50)` (Y) · `section varchar(30)` (Y) · `length_mm numeric(12,2)` (Y) · `weight_kg numeric(12,3)` (Y) · `weight_source varchar(12)` (Y) · `captured_json jsonb` (Y — the charging input parameters kept until the final weight) · `inventory_id` FK `mes_inventory` (Y — the placeholder inventory row under the virtual number) · `authorised_by bigint` · `authorised_at timestamptz` · `status varchar(15)` (OPEN / RECONCILED / SCRAPPED / CANCELLED) · `erp_pending boolean` · `reconciled_inventory_id` FK `mes_inventory` (Y) · `reconciled_batch_number varchar(60)` (Y) · `reconciled_by bigint` (Y) · `reconciled_at timestamptz` (Y) · `l2_pushed_at timestamptz` (Y) · `alert_after_days int` (Y) · **+ audit tail**.
- `mes_inventory` gains `virtual_id` FK `mes_virtual_id` (Y) · `identity_kind varchar(10)` (ACTUAL / PLANNED / VIRTUAL).
- **R-OPS-11 — creation (VID-001…004, 9.6 additional point):** a NOT_FOUND scan on a known heat runs the missing-number check — planned numbers of the heat (heat generation and schedule children) minus produced numbers; a gap proposes the virtual number = the planned number, so the built planned → actual cascade renames it on arrival; with no known heat the number is `VID-{unit}-{yyyymmdd}-{seq}`. Creation needs the privileged action VIRTUAL_ID_CREATE (a super-user, not every operator); the placeholder inventory row carries the captured parameters and charges, rolls and confirms like any material. - **R-OPS-54 — dispatch and weight (DSP-001…003, F9.4-05…07):** the weight declared at dispatch is stored on the pack with the variance and posts a WEIGHT_CORRECTION row; Σ declared output of a lot ≤ its net input (BLOCK — the mass-balance check of the card); the two-order confirmation is the PPC order link with the GMM_DISPATCH swap; `required_production_date = dispatch_due_date − tempering_buffer_days − lead_time_days` on the schedule line; rework and retrial run as the built rework flow (`is_rework`).
- **R-OPS-55 — save workflow (PCK-006):** the confirmation is one-way; `confirm_warning_text` shows the configurable warning before the final save; the ERP queue row is written on save (AUTO) or released by the operator (MANUAL).
