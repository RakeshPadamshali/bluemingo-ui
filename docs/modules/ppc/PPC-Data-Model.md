# JSW MES v2 — PPC (Order Book, Campaign Planning & Scheduling): data-model design (Phase 2, pass 3)

**Date:** 2026-09-15 · **Status:** design draft v0.1 for review · **Scope:** BRD §7 (21 headings, 50 requirement rows) / epic E7 (76 stories incl. the `F7.2-01` duplicate pair) and the 21 reviewed rows of `PPC_Section_7_functional _gap (Bluemingo review).xlsx`; the 17 design items of area 2 in the Phase 2 backlog.
**Basis:** the live production-confirmation application (orders 1,201 / lines 5,585 with type, routing, delivery date, pending quantity and TDC number; schedules → schedule materials → children with order-line pegging; casting-plan upload and heat generation; rolling-program upload and manual sequencing; material charging; batch / order allocation tables; planner integration with mirrored plan tables; no scheduled jobs; no SAP interface) and the Allocation / MRP application (9-stage allocation with attribute matching, 1-D nesting, multi-hop MRP, computed strategies; release / un-release; block-release constraint; `Order_Line_Details.priority`; no swap object). The MDM design supplies the masters this pass consumes (length, yield, family / section load, MoQ, ferro-alloy norms, swap rules, customer priority / order-book rules, pit cooling, annealing load, form conversion, batch derivation, downtime). Every "exists" claim was checked on 2026-09-15.
**Scope rules in force (2026-09-12):** platform foundations deferred (approvals P1, notifications P2, effective dating P3, devices P4, integration platform P5, documents P6) — content named; integration designed MES-side only (SAP order feed, SAP status sync, SMS MES batch feed, casting-plan hand-off, FP reference plan); assumptions flagged: **constraint rules live inside MES as configuration `[assumption — D-02]`**, ABGM in scope `[assumption — D-05]`, the Allocation application's pull becomes the permanent SMS → Mills link until the caster boundary is decided `[assumption — D-07]`, roles named not enforced `[assumption — D-03]`.

## 0. Organisation

### 0.1 Ownership and landing
PPC is a **platform** module: its tables belong to the production-confirmation application (`mes_*`, MES PC Flyway) and are raised as change requests **PPC-R-01 … PPC-R-16** in `Requests-PPC.md`; the Allocation application receives **ALC-R-05 … ALC-R-08**. Nothing is QA-owned except the read of PSN data (CQ design) and the pit-cooling / grinding rules (MDM). Nothing inside either application is coded from here.

### 0.2 Conventions
As the QA Data-Model §2 and the MDM design §0.2: PK `<entity>_id bigint`; **`+ audit tail`**; `(Y)` nullable; scope keys and resolution rule **R-S**; `effective_from/to` informational until P3. Product-agnostic per D0: units (SMS, BRM, BLM, ABGM, Annealing, GMM, Bright Bar) are `mes_operations` / `mes_factories` rows; product types, order categories, SAP order types, stages and constraint types are data. "Stage" = a production step of the order's routing (cast, roll, downstream, FGHO) resolved from `mes_operations`.

### 0.3 Live facts that shaped the design (verified 2026-09-15)
- `mes_order_line_items` carries `order_type` (all rows MTO), `status` (all RELEASED), `pending_quantity`, `pending_nop`, `routing_id`, `delivery_date`, `tdc_no` (NULL everywhere); `mes_orders.order_source` = Local; the CQ pass adds `tdc_id` + `psn_revision_no` (CQ-R-02).
- Pegging exists at three places: `mes_schedule_material_childs.order_line_id`, `mes_schedule_material_allocations` (child × order line × qty), `mes_batch_order_allocation` (batch × order line × qty), `mes_order_inventory` (lot × order line, deactivate-never-delete), `mes_inventory_order_allocation`. **The batch ↔ order-line allocation table is the anchor for swapping.**
- `mes_schedules` (factory, operation, equipment, `is_hold`, `charge_status`) → `mes_schedule_materials` (plan_id, source_system / source_ref / pulled_at from the Allocation pull) → `mes_schedule_material_childs` (planned_seq, planned_equipment_id, stage_item_code, pieces) is the execution queue the Confirmation screen reads; Manual Sequencing re-orders it; the Allocation pull marked ADHOC / TEMPORARY builds it from released heats.
- `mes_pln_details` (478 plans) and `mes_pln_*` mirror the external planner's output — reference only (F7.13-02).
- Casting-plan upload packs 25 t heats and drops < 9 t tails (`CastingPlanHeatBuilder`); heat generation and the casting reconciliation (`mes_production_allocation_deviation`: FULL / PARTIAL / OVER / NONE) exist; there is **no casting indent object** — the plan comes in by Excel.
- `mes_inventory` carries `prev_operation` / `next_operation`, `state`, `ud_status`, `routing_complete` — **no equipment and no yard location**; `mes_material_sequence.planned_equipment_id` is the only equipment hint.
- Consumable actuals per confirmation exist (`mes_consumable_usage`, auto-calculated from norms); `mes_product_order_forecast` is an empty container.
- No swap object on either surface; the Allocation application's `Mst_Compatible_Value` and attribute match engine serve allocation, and `mes_audit_log` carries ALLOCATION_RELEASE events.

## 1. Cross-cutting decisions for PPC

| # | Decision | Rationale |
|---|---|---|
| **M-PPC-01** | **One order book, one line table.** The SAP sales order, its production order and the MES production orders are rows of `mes_orders` / `mes_order_line_items` / `mes_production_order`; internal, ISO, NCO, trial and development orders are the same rows with an `order_category`; ZSDP dispatch orders are lines with `planning_relevant = false`. | BRD OMB-002/005/006, 7.1.3: one source of truth for planning, BTP, allocation and campaigns; the built order screen, import and pegging keep working. |
| **M-PPC-02** | **Balances are a computed snapshot per line per stage** (`mes_order_stage_balance`), refreshed per shift and on events, not derived on the fly by every screen. | OMB-007/010: BTC / BTR / BTP / BTD / OTIF by stage with yield factors; one place every screen and report reads. |
| **M-PPC-03** | **Allocation stays where it is; swapping is a new transaction over it.** A swap re-points `mes_batch_order_allocation` rows (and the lot / schedule pegging) in one transaction, records every line with its rule evaluation, and is reversible as a new transaction. | 7.2.2: five scenarios, auto-swap, reverse, log — none exists; the pegging tables do. |
| **M-PPC-04** | **Campaign and rolling schedule are distinct artefacts** (SEQ-009): the campaign is the multi-day, multi-product commitment; the rolling schedule is the size sequence for a day / shift that releases into the built execution queue (`mes_schedules`). | The built queue and sequencing are kept as the execution layer. |
| **M-PPC-05** | **Constraints are configuration inside MES** `[assumption — D-02]`: a constraint master per unit with type, parameters, precedence and enforcement; feasibility results are stored per campaign order and schedule block; the planner's plan remains a reference tab. | BRD 7.3.2 CST-001, F7.13-02 (MES runs without FP). |
| **M-PPC-06** | **The SMS → Mills batch feed is a staging table with idempotent upsert** into the built schedule / inventory tables; the Allocation pull's read model is reused as the first feed `[assumption — D-07]`. | MAT-001/002: near-real-time, validated, with discrepancy flags; the pull is ADHOC today. |
| **M-PPC-07** | **Casting hand-off is an indent object** (`mes_casting_indent`) with BTC, lengths, priority lock and required date; the SMS MES receives it (interface deferred) and the built casting-plan upload / heat generation consume it. | CMP-005/006, 7.5: the plan must be sent from Mills MES to SMS MES with mandatory attributes. |
| **M-PPC-08** | **Engines deferred, content designed:** approvals (HOD, PPC-HOD finalisation, super-user holds) are named actions on the MDM privileged-action master; alerts are events; SAP messages are staging rows with status. | Scope decision 2026-09-12. |
| **M-PPC-09** | **Masters come from the MDM design** (length, yield, family / section load, MoQ, swap rules, customer priority, order-book rules, ferro-alloy norms, annealing load, form conversion, batch derivation, pit cooling, grinding). No PPC-local copy. | One book of record. |

## 2. Order book

### 2.1 `mes_orders` / `mes_order_line_items` — header and line extensions *(rows 2, 3, 5; OMB-001…006, 7.1.3, F7.1-07, F7.1-09)* — PLATFORM
- `mes_orders` gains: **`order_category varchar(20)`** (SAP_SALES / ISO / INTERNAL_REF / INTERNAL_NEW / NCO / TRIAL / DEVELOPMENT / DISPATCH_ONLY / STO_INBOUND — data) · **`sap_order_type varchar(10)`** (Y — ZFAC / ZEXP / ZISO / ZFAX / ZSDP … data) · `sap_order_no varchar(30)` (Y) · `sap_status varchar(20)` (Y — OPEN / CLOSED / SHORT_CLOSED / ON_HOLD, from the status sync) · `sap_status_at timestamptz` (Y) · `reference_order_id` FK `mes_orders` (Y — internal order created *with reference*) · `planning_relevant boolean` (default true; ZSDP false unless PPC overrides) · `planning_override_by bigint` (Y) · `marketing_rank int` (Y — CMP-004 manual override rank) · `trial_flags_json jsonb` (Y — trial / development / CAPA flags that propagate to every line, batch and screen) · `plant_of_supply varchar(30)` (Y — STO source plant) · `job_work_vendor_id bigint` (Y — job-work routing) · `received_at timestamptz` (Y).
- `mes_order_line_items` gains: **`psn_no varchar(40)`** (Y — denormalised from the CQ pin `tdc_id` / `psn_revision_no`) · `section_shape varchar(30)` (Y) · `section_size numeric(12,3)` (Y) · `input_section varchar(30)` (Y — from the PSN / VC, F7.2-10) · `grinding_required varchar(15)` (Y — resolved from the grinding rules) · `length_tolerance_mm numeric(9,2)` (Y) · **`release_qty numeric(18,4)`** (Y — production release quantity distinct from the SAP quantity, OMB-012) · `released_by bigint` (Y) · `released_at timestamptz` (Y) · `dispatched_qty numeric(18,4)` (Y — SAP reference) · `fgho_qty numeric(18,4)` (Y — finished-goods hand-over, OMB-008) · `rejected_qty numeric(18,4)` (Y) · `diverted_qty numeric(18,4)` (Y — swapped out) · `short_closed_qty numeric(18,4)` (Y) · `hold_status varchar(10)` (Y — HELD / null) · `slot_score numeric(9,3)` (Y — computed, 2.8) · `sla_delivery_date date` (Y — contractual date used for OTIF) · `otif_status varchar(15)` (Y — ON_TRACK / AT_RISK / LATE / DELIVERED_OTIF / DELIVERED_LATE) · `flags_json jsonb` (Y — inherited trial / development flags).
- **Vocabulary rules:** `order_category` decides planning behaviour (R-PPC-01); `sap_order_type` decides default inclusion (ZSDP excluded, all other Z-types included, OMB-005); an INTERNAL_REF order inherits every attribute of its reference order and needs no approval; INTERNAL_NEW needs the PPC approval action; NCO needs grade, PSN, output size and bloom length (R-PPC-12).

### 2.2 `mes_production_order` — MES production orders split from the SAP order *(rows 4, 14; BRM-011, OMB-012)* — PLATFORM
- **`mes_production_order`** — `production_order_id` PK · `production_order_no varchar(40)` UQ (generated: series in `mes_batch_number_generation_config` pattern) · `order_line_id` FK `mes_order_line_items` · `sap_production_order_no varchar(30)` (Y) · `unit_operation_id` FK `mes_operations` (the producing unit) · `quantity numeric(18,4)` · `unit_id` FK `mes_units` · `campaign_id` FK `mes_campaign` (Y) · `status varchar(15)` (DRAFT / RELEASED / IN_PROGRESS / COMPLETED / CANCELLED) · `released_by bigint` (Y) · `released_at timestamptz` (Y) · `remarks varchar(255)` (Y) · **+ audit tail**.
- Confirmation happens against the released MES production order (BRM-011); the sum of active production orders of a line may not exceed `release_qty` (R-PPC-03). The Confirmation screen's queue keeps reading `mes_schedules`; the production order is the commercial envelope the schedule belongs to (`mes_schedule_materials.production_order_id`, extension in 4.6).

### 2.3 `mes_order_stage_balance` — BTC / BTR / BTP / BTD / OTIF by stage *(row 3; OMB-007…011, BRM-010, F7.1-01, F7.11-01, F7.6-03)* — PLATFORM
- **`mes_order_stage_balance`** — `balance_id` PK · `order_line_id` FK · **`stage_operation_id`** FK `mes_operations` (SMS cast / BRM or BLM roll / ABGM / Annealing / GMM / Bright Bar / FGHO — the stages of the line's routing) · `stage_code varchar(20)` (CAST / ROLL / PROCESS / FGHO — data label) · `order_qty numeric(18,4)` · `release_qty numeric(18,4)` (Y) · `produced_qty numeric(18,4)` (confirmed at this stage) · `wip_qty numeric(18,4)` (in process at this stage) · `upstream_wip_qty numeric(18,4)` (material pegged to the line at earlier stages, yield-adjusted) · `rejected_qty numeric(18,4)` · `diverted_qty numeric(18,4)` · `inter_plant_qty numeric(18,4)` (Y — STO material expected, OMB-011) · `fg_qty numeric(18,4)` · `fgho_qty numeric(18,4)` · `dispatched_qty numeric(18,4)` (reference) · `yield_factor numeric(7,4)` (from the MDM yield master, resolved for the stage) · **`balance_qty numeric(18,4)`** (the BTC / BTR / BTP of the stage) · `balance_pieces int` (Y) · `computed_at timestamptz` · `computed_by varchar(20)` (SHIFT_JOB / EVENT / MANUAL) · **+ audit tail**. UQ (`order_line_id`, `stage_operation_id`).
- **R-PPC-02 — balance formula (BRM-010, 7.5 table):** for a stage S, `balance = (order_qty or release_qty when set) − produced_at_S + rejected_at_S + diverted_out_at_S − upstream_wip_covering_S`, where `upstream_wip_covering_S` = Σ (pegged upstream quantity × cumulative yield from its stage to S) and FGHO uses `fgho_qty` (not dispatch, OMB-008). Worked example (7.5): SO 100 t, cast 90 t, rejected / diverted 15 t → **BTC 25 t**; with 10 t of pegged as-cast WIP at 96 % gross yield covering the roll stage, BTR = 100 − 0 + 0 − 9.6 = 90.4 t. Refresh every shift (a scheduled job of the PPC service) and on confirmation, UD, swap, amendment and inter-plant receipt events.
- **R-PPC-04 — OTIF:** `otif_status` from the order-book rules (MDM OTIF_WINDOW): ON_TRACK when the projected FGHO date (from the campaign / schedule) is within the window, AT_RISK when the balance cannot be covered by released schedules before the window, LATE when the window has passed with balance > 0, DELIVERED_OTIF / DELIVERED_LATE after FGHO.

### 2.4 `mes_order_inbound` — SAP / SFDC order messages, MES side *(rows 3, 10; OMB-001, F7.1-08, SWP-009/010; integration deferred)* — PLATFORM
- **`mes_order_inbound`** — `inbound_id` PK · `source varchar(10)` (SAP / SFDC / FP / EXCEL) · `message_type varchar(20)` (SO_CREATE / SO_AMEND / SO_STATUS / SO_HOLD / DISPATCH / PO_CREATE) · `external_ref varchar(60)` (SAP order + item) · `payload_json jsonb` · `received_at timestamptz` · `status varchar(15)` (RECEIVED / APPLIED / REJECTED / SKIPPED) · `applied_order_line_id` FK (Y) · `error_text varchar(500)` (Y) · `correlation_id varchar(60)` (Y) · **+ audit tail**.
- **R-PPC-05 — apply rules:** SO_CREATE / SO_AMEND upsert the order and line (amendments create `mes_order_amendment` rows, 2.5); SO_STATUS updates `sap_status` — a CLOSED / SHORT_CLOSED status on a line with charging or rolling begun in MES is **not applied** but raised to PPC (`PPC_SAP_CLOSURE_CONFLICT`) until PPC confirms (SWP-010); SO_HOLD applies a hold with source SAP (2.6); DISPATCH updates `dispatched_qty` (reference); codes resolve through the MDM external code map. The Excel import remains as the fallback source. Message contracts and transport are deferred (D-01).

### 2.5 `mes_order_amendment` — amendments, tolerance, short-close *(row 4; OMB-012…016, F7.1-02, F7.1-05, F7.1-06)* — PLATFORM
- **`mes_order_amendment`** — `amendment_id` PK · `order_line_id` FK · **`amendment_type varchar(25)`** (RELEASE_QTY / QTY_INCREASE / QTY_REDUCE / SHORT_CLOSE / TOLERANCE_OVERRUN / TYPE_INCLUDE / DELIVERY_DATE / SAP_AMEND) · `old_value varchar(100)` (Y) · `new_value varchar(100)` (Y) · `qty_delta numeric(18,4)` (Y) · `reason varchar(500)` · `source varchar(10)` (PPC / SAP / MARKETING) · `requires_approval boolean` · **`approval_status varchar(15)`** (NOT_REQUIRED / PENDING / APPROVED / REJECTED) `[assumption — D-03]` · `approval_action_code varchar(50)` (Y — ORDER_AMEND_APPROVE / TOLERANCE_OVERRUN_APPROVE, privileged actions) · `approved_by bigint` (Y) · `approved_at timestamptz` (Y) · `applied boolean` · **+ audit tail**.
- **R-PPC-06 — tolerance matrix (OMB-014):** the MDM order-book rule type **TOLERANCE_MATRIX** carries bands in `param_json` (e.g. `[{"upto_t":5,"pct":30},{"upto_t":10,"pct":20},{"above":true,"pct":10}]`); production or a quantity change within the band of the line's order quantity needs no approval; beyond it a TOLERANCE_OVERRUN amendment is raised with a documented reason and the HOD approval action. Worked example: 8 t order → ±20 % → 9.6 t ceiling; a request to produce 10 t raises the approval.
- **R-PPC-07 — rejections reduce the balance automatically** (F7.1-06): a rejected quantity at usage decision adds to `rejected_qty` and the stage balance recomputes (no amendment row); short-close writes `short_closed_qty` and a SHORT_CLOSE amendment (posting to SAP deferred).

### 2.6 `mes_order_hold` — hold and release, single and mass *(row 4; OMB-015, F7.1-03)* — PLATFORM
- **`mes_order_hold`** — `hold_id` PK · `order_line_id` FK · `hold_reason_id` FK `mes_hold_reasons` (applied-at = Order, MDM §3.10) · `source varchar(10)` (PPC / SAP / SFDC) · `held_by bigint` · `held_at timestamptz` · `released_by bigint` (Y) · `released_at timestamptz` (Y) · `release_note varchar(255)` (Y) · `batch_ref varchar(40)` (Y — mass-action batch id) · **+ audit tail**.
- **R-PPC-08:** a held line (`hold_status = HELD`) is excluded from every scheduling screen (campaign, casting indent, rolling schedule, ABGM, annealing, GMM, bright bar); a hold arriving from SAP / SFDC applies automatically with source SAP; only the PPC super-user actions (ORDER_MASS_HOLD / ORDER_MASS_RELEASE, MDM §2.6) may mass-hold or mass-release; single holds need the PPC role. Every event is audited with user, time and reason (OMB-016).

### 2.7 Internal, ISO, NCO and trial orders *(rows 5, 15; OMB-006, 7.1.3, BRM-ISO-01…05, F7.4-04)* — PLATFORM
No further tables: `order_category` + `reference_order_id` on `mes_orders` (2.1) and the swap engine (3.3) carry them.
- **R-PPC-09 — ISO / internal:** an ISO or INTERNAL_NEW order is created by PPC (mandatory grade, PSN, output size, bloom length for NCO / ISO casting); material produced against it is *free* for allocation (3.2) and is re-attached to a customer order by the ISO_TO_SO swap scenario (3.3); if none arrives by FG readiness the batch is handed to SAP as unrestricted stock under the ISO reference (interface deferred).
- **R-PPC-10 — trial / development:** flags in `trial_flags_json` propagate to every line, production order, schedule block and batch (`flags_json` on the line; the confirmation screen shows the flag and relaxes PSN parameter validation to WARN for flagged trial orders, OPEN-PPC-3); development orders use the development category of the CQ design (CQ-R-03).

### 2.8 Customer priority and weighted slotting *(row 6; CPS-001/002, CMP-004, F7.4-03)* — PLATFORM (masters in MDM)
- Masters: `mes_customer_priority` (tier, OTIF target, commit window) and the order-book rule **SLOTTING_WEIGHTS** (`param_json`: weights for tier, delivery proximity, ageing, marketing rank) — MDM §3.10.
- **R-PPC-11 — slot score:** `slot_score = w_tier × tier_score + w_date × proximity_score + w_age × ageing_score + w_mkt × marketing_rank_score`, each component normalised 0–1 within the planning window; stored on the line and recomputed with the balances; campaign and casting screens sort competing orders by score, priority-locked orders first (5.2). Worked example: weights 0.4 / 0.3 / 0.2 / 0.1; tier 1 (1.0), delivery in 3 days of a 14-day window (0.79), ageing 20 days of max 60 (0.33), marketing rank 2 of 10 (0.9) → 0.40 + 0.24 + 0.07 + 0.09 = **0.80**.

## 3. Batches, allocation and swapping

### 3.1 `mes_sms_batch_feed` — SMS → Mills batch flow, MES side *(row 8; MAT-001/002, F7.2-03; D-07 assumption)* — PLATFORM
- **`mes_sms_batch_feed`** — `feed_id` PK · `source_system varchar(20)` (SMS_MES / ALLOCATOR_PULL / EXCEL) · `source_ref varchar(60)` (Y) · `batch_number varchar(60)` · `heat_number varchar(100)` · `grade varchar(50)` (Y) · `section varchar(30)` (Y) · `psn_no varchar(40)` (Y) · `tdc_no varchar(50)` (Y) · `quantity numeric(18,4)` · `pieces int` (Y) · `length_mm numeric(12,2)` (Y) · `inspection_status varchar(20)` (Y — from SMS QA: CLEARED / HOLD / PENDING) · `sap_order_no varchar(30)` (Y — pre-allocation) · `order_line_id` FK (Y — resolved) · `received_at timestamptz` · `status varchar(15)` (RECEIVED / APPLIED / DISCREPANCY / REJECTED) · `applied_batch_id` FK `mes_batches` (Y) · `applied_inventory_id` FK `mes_inventory` (Y) · `error_text varchar(500)` (Y) · **+ audit tail**. UQ (`source_system`, `batch_number`, `heat_number`).
- **R-PPC-13 — apply:** an APPLIED row upserts the batch / lot (`mes_batches`, `mes_inventory` with `material_form_id` billet / bloom) and, when a confirmed order is named, the pre-allocation (3.2) after validating grade, section and quantity against the line; a mismatch writes a discrepancy row (3.2) and leaves the batch free. The Allocation pull's read model (`AllocatorReadService`) is the first producer of feed rows, run on a schedule instead of on demand; the SMS MES direct feed replaces it when the caster boundary is decided (D-07). Near-real-time = the feed job interval (policy PPC_FEED_MINUTES, default 5).

### 3.2 Allocation extensions and discrepancies *(rows 7, 8, 20; MAT-003…005, F7.2-03, F7.3-03, F7.12-01/04)* — PLATFORM
- `mes_batch_order_allocation` gains: **`source varchar(15)`** (SMS_PREALLOC / MANUAL / AUTO / SWAP / ALLOCATOR) · `status varchar(15)` (ACTIVE / RELEASED_TO_MILL / CONSUMED / REVERSED) · `allocated_by bigint` (Y) · `validation_json jsonb` (Y — attribute checks: grade, PSN, section, input size, length; result per attribute) · `soft_mismatch boolean` · `override_by bigint` (Y) · `override_reason varchar(255)` (Y) · `swap_transaction_id` FK `mes_swap_transaction` (Y) · `stage_operation_id` FK (Y — the stage at which the allocation was made).
- **`mes_batch_link_discrepancy`** — `discrepancy_id` PK · `batch_id` FK `mes_batches` · `order_line_id` FK (Y) · `attribute_code varchar(50)` (GRADE / SECTION / QTY / PSN / LENGTH) · `expected_value varchar(100)` · `actual_value varchar(100)` · `severity varchar(10)` (HARD / SOFT) · `status varchar(15)` (OPEN / OVERRIDDEN / RESOLVED) · `resolved_by bigint` (Y) · `resolved_at timestamptz` (Y) · `note varchar(255)` (Y) · **+ audit tail**.
- **R-PPC-14 — attach free batches:** the material-allocation screen lists free batches (no ACTIVE allocation) with **eligible orders** suggested by attribute matching (grade and PSN mandatory; section and input size mandatory; length within `length_tolerance_mm` soft, default ± 100 mm); a soft mismatch may be overridden by PPC with a reason; a hard mismatch cannot. Under-inspection stock may be allocated (F7.12-04) but not charged until cleared. The eligibility routine is the swap-rule evaluation of 3.3 with scope FREE_TO_SO, so allocation and swapping share one compatibility rule set.

### 3.3 `mes_swap_transaction` / `mes_swap_line` — the swapping engine *(rows 7, 9, 10, 20; 7.2.2, SWP-002…013, MAT-006/007, F7.12-02, F7.6-02, F7.7-01)* — PLATFORM
- **`mes_swap_transaction`** — `swap_transaction_id` PK · `swap_no varchar(30)` UQ · **`scenario varchar(20)`** (BATCH_TO_BATCH / FREE_TO_SO / CROSS_SO_PARTIAL / REVERSE / ISO_TO_SO / AS_ROLLED_TO_ANNEALING / GMM_DISPATCH — data) · `mode varchar(10)` (MANUAL / AUTO) · `stage_scope varchar(20)` (SEQUENCING / CHARGING / WIP / ANNEALING / GMM) · `target_order_line_id` FK · `target_qty numeric(18,4)` (Y) · `requested_by bigint` · `requested_role varchar(30)` (PPC / MILL_PLANNER / MILL_OPS) · `yms_reliability_on boolean` (auto-swap ordering toggle) · `status varchar(15)` (DRAFT / VALIDATED / EXECUTED / REVERSED / REJECTED) · `executed_at timestamptz` (Y) · `reverse_of_id` FK `mes_swap_transaction` (Y) · `approval_action_code varchar(50)` (Y — SWAP_APPROVE when a soft rule failed) · `approved_by bigint` (Y) · `comment varchar(500)` (Y) · **+ audit tail**.

### 4.6 Release into execution — the built Rolling Program and Manual Sequencing *(rows 11, 12; F7.2-05, F7.3-05)* — PLATFORM (built queue reused)
What runs today (verified in code 2026-09-15): the **Rolling Program** is an Excel rolling sheet imported per program date (`mes_rolling_program`, one row per Demand UID + heat with F / S / rec size, grade, lengths, pieces, weight, category, execution, HT condition), each row checked against RM inward and against the metal (`RollingProgramMaterialCheck` → verdict SEQUENCABLE) and matched to lots by the Demand UID stamped on the lot; **Manual Sequencing** then shows the matched lots per operation, the planner drags the order and assigns mills (`RollingMillAssignmentService`: mill from the product-category master, vetoed by the order line's double-rolled flag) and saves positions per (operation, planned equipment) — lot grain into `mes_material_sequence`, schedule-material grain into `mes_schedule_material_childs.planned_seq`. The design keeps both as the **execution layer under the rolling schedule**:
- `mes_schedule_materials` gains **`rolling_schedule_id` FK (Y)** · **`block_id` FK (Y)** · **`production_order_id` FK (Y)**; `mes_schedules` gains `rolling_schedule_id` FK (Y); **`mes_material_sequence` gains `block_id` FK `mes_rolling_schedule_block` (Y)**.
- `mes_rolling_program` gains **`source varchar(10)`** (UPLOAD / SCHEDULE) · `rolling_schedule_id` FK (Y) · `block_id` FK (Y); `mes_rolling_program_upload` gains `origin varchar(10)` (EXCEL / SCHEDULE) · `rolling_schedule_id` FK (Y).
- **R-PPC-29 — release generates the rolling program (F7.2-05, F7.3-05):** RELEASED creates one **schedule-origin rolling-program upload** with one program row per pegged batch / Demand UID of each block, in block order, carrying the block's size, grade, rolled length, pieces and weight and the order line's execution / HT condition; the built RM-inward and material checks run on every row (only SEQUENCABLE rows enter the queue, the rest are listed as exceptions on the schedule); the queue rows (`mes_schedules` / `mes_schedule_materials` / children) are written in block order with `planned_seq` pre-set and the mill from the block (`mill_operation_id`) refined by the built mill assignment; production orders go RELEASED. The Excel upload stays as the fallback path (no campaign) and produces rows with `source = UPLOAD` and no block.
- **R-PPC-29a — Manual Sequencing inside the block:** the planner keeps drag-drop and mill assignment on the released queue; moving lots **within a block** is free; moving a lot **across blocks** (which changes the agreed size / grade order) or into a different mill after ACCEPT is a schedule change: it re-stamps `block_id`, writes the change log and raises PPC_SCHEDULE_CHANGED (R-PPC-26). DUMMY (size-setting) lots keep their built marking. Free batches in a block are flagged (SWP-003).
